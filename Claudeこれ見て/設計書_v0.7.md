## 1. 概要

### 1.1 目的
ギターの練習に必要な機能だけを1つのアプリにまとめ、**考えずに練習を始められる環境**を提供する。

解決する問題:
- 練習のたびに、音作りのソフト(DAW)、YouTube、タブ譜ソフトを行き来する
- 既存ツールは機能が多く、設定に時間を取られ、何をすればいいか分からなくなる
- 演奏中は手が塞がっていて、細かい操作が難しい

### 1.2 ターゲット【確定】
- **主なユーザー**: PCでギターの音を出せる環境(オーディオインターフェースとドライバ)をすでに持っているが、PCやプラグインに詳しくない人
- **第2のユーザー**: VST3プラグインを使う中級者(作者自身を含む)。詳細設定で対応する
- **対象外**: 実機アンプだけで弾く人(Guitar Pro 8で足りる)、PCでギターの音を出さない人

### 1.3 既存ツールとの違い【確定】
一言でいうと「**練習するためだけのアプリ**」。

| 既存ツール | 取り入れるもの | 取り入れないもの・課題 |
| --- | --- | --- |
| Guitar Pro 8 | タブ譜の表示、音源との同期 | 高度なタブ譜作成、MIDI再生が中心の機能 |
| Reaper(DAW) | プラグインで楽器の音を出す部分 | 録音、作曲、ミックス |
| スマホアプリ | ― | 画面・端子の制約で、音出し・音源・タブ譜を同時に使えない |
| Webアプリ | ― | 遅延と音質。結局タブを複数開く |

**作らないもの**: 録音、作曲、ミックス、MIDIの打ち込み、YouTube以外の配信サービス、音声のダウンロード、macOS対応

### 1.4 成功指標【確定】

| 指標 | 目標 |
| --- | --- |
| 保存済みセッションを再開してから、弾き始めるまで | **3クリック以内**(セッションを選ぶ→再生) |
| ギター経路の遅延(ドライバ報告値、48kHz/バッファ256) | **約26ms以内** |

### 1.5 優先順位【確定】
① 使いやすさ ② 低遅延 ③ 反応の速さ。トレードオフはこの順で判断する。

## 2. 主な設計判断

開発の過程で行った判断と、その理由です。

| # | 判断 | 理由 |
| --- | --- | --- |
| 1 | **ターゲットを「PCで音は出せるが、プラグインに詳しくない人」に絞った** | 当初は初心者向けと中級者向けの機能が混在し、誰のためのアプリか曖昧だった。機材の接続はアプリでは解決できないため前提条件として切り分け、アプリが解決すべき範囲をはっきりさせた |
| 2 | **機能を増やすのではなく、絞って1か所にまとめる** | 調べると、Guitar Pro 8にもReaperにも練習に使える機能はあった。価値は機能の多さではなく、「考えずに始められること」にあると整理した |
| 3 | **Web音源をYouTubeのみにし、ブラウザの音をアプリに取り込む方式を廃止** | 速度変更・ループ・タブ譜との同期は、アプリが再生を操作できる音源でしか成り立たない。YouTubeには操作用のAPIがある。要件を見直したことで、**最も技術的なリスクが高かった処理そのものを不要にできた** |
| 4 | **ローカル音源とYouTubeの両方に対応** | 音源ファイルを持っていない人も多いため、YouTubeは外せない。ローカル音源は最も正確に制御でき、同期・速度変更の土台になる |
| 5 | **タブ譜の表示にalphaTabを採用** | 描画を自作すると期限に間に合わない。alphaTabはオフラインで動き、YouTubeや外部音源との同期の仕組みも持つ。自分は本作品の中心である「同期」と「操作性」に集中する |
| 6 | **音色は内蔵プリセット(NAM)を主役に、VST3は詳細設定へ** | ターゲット(#1)はプラグインの知識がない。開いてすぐ良い音が出ることを優先した |
| 7 | **ミキサーは「音源・ギター・メトロノーム」の3系統のみ** | 練習に必要なのは、この3つのバランスだけ。#3と合わせ、実装も大幅に簡単になった |
| 8 | **遅延目標を「10ms未満」から「約26ms(ドライバ報告値)」に変更** | 作者が実際に違和感なく弾けている設定(48kHz/256で25.8ms)を根拠にした。処理に余裕ができ、音切れのリスクも下がる。測り方は、一般的な機材と同じドライバ報告値に統一した |
| 9 | **「キーボード全廃」から「演奏中の操作はマウスで完結」へ** | 本当の目的は「演奏中に手を止めさせない」こと。準備段階の文字入力やショートカットまで禁止する必要はないと整理した |
| 10 | **曲ごとの「セッション」を保存・復元の単位にする** | 1曲を集中して練習する実際の使い方に合わせた。前回の状態がそのまま戻るので、3クリックで練習を再開できる |
| 11 | **BPMは「タブ譜 → ネット取得 → 手入力・タップ」の順で決める** | タブ譜のテンポが最も確実。Spotifyのテンポ取得APIは2024年11月に新規向けの提供が終わっており、代替サービスは精度にばらつきがあるため、自動取得は「候補」として扱い、必ず手で直せるようにした |
| 12 | **C++とJUCEを採用(Rustも検討)** | Rustは安全性が魅力だったが、Windowsでのプラグインのホスト機能がまだ発展途上だった。JUCEは低遅延の音声処理、VST3、WebView連携が一式そろう。ライセンスはAGPLv3(無償)で、将来の無償公開と両立する |
| 13 | **Windowsのみに対応** | 低遅延の音声処理の中心であるASIOがWindows中心の技術。期限内に1つのOSで完成度を上げることを優先した |
| 14 | **コミュニティの音色(TONE3000)は同梱せず、オンライン取得の拡張機能に** | 個々の音色データは投稿者の著作物で、再配布の許可がない。公式の数点(MIT)だけ同梱し、残りはユーザーが自分で取得する。基本機能はオフラインで成り立つ |
| 15 | **オーディオ処理のスレッドで、メモリ確保・ロック・ファイル操作を禁止** | 音切れを防ぐための規約。C++はコンパイラがこれを守ってくれないため、設計段階で明文化した |
| 16 | **一覧と設定はネイティブ(JUCE)、練習画面はWebView(HTML/CSS)で描く。見た目はHTMLで決めてからネイティブに移す** | WebView2は初回の起動に時間がかかり、Microsoftも最初の画面には使わないよう勧めている。起動画面をネイティブにして速さを守り、一覧を表示している間に裏でWebViewを準備する。一方、練習画面はタブ譜とYouTubeのためにどのみちWebViewが要り、HTMLで作るとデザインツール(Impeccable)をそのまま使える |
| 17 | **見た目のコンセプトは「リハーサルスタジオ」** | 練習部屋の暖かさと、スタジオでメンバーと合わせる空気感を表す。土台は集中しやすい寒色、アクセントは真空管のような琥珀色1色にし、落ち着きと個性を両立した |

## 4. 利用の流れ・画面・デザイン

### 4.1 利用の流れ【確定】
1. セッション一覧から、新しいセッションを作る(保存済みのものを開くこともできる)
2. 音源を選ぶ: ファイル、またはYouTubeのURL(貼り付けボタンを押したときだけクリップボードを読む)
3. タブ譜を選ぶ(任意【提案】)
4. 音色をプリセットのカードから選ぶ
5. BPMを確認する(違えば手入力かタップで直す)
6. 練習する。終わったら保存して、一覧に戻る

### 4.2 セッション画面(たたき台)【提案】

```
┌──────────────────────────────────────────────────────────────────┐
│ [◀ 一覧]  曲名                                   [保存]  [⚙詳細] │
├────────────────────────────────────────────┬─────────────────────┤
│                                            │ [YouTubeの動画]      │
│        タブ譜(再生カーソルが自動スクロール) ├─────────────────────┤
│                                            │ 音色: [クリーン][歪み]│
│                                            │ 音源 ▮▮▮▯ ギター ▮▮▮▯ │
│                                            │ メトロノーム ▮▮▯▯     │
├────────────────────────────────────────────┴─────────────────────┤
│ [◀◀] [ 再生/停止 ] [▶▶]  速度 80%  BPM 120 [ TAP ]  A──B  [チューナー] │
└──────────────────────────────────────────────────────────────────┘
```

### 4.3 操作の原則【確定】
- **ホイール**: カーソルが乗っている部品(速度、BPM、ループ範囲、音量、ずらし量)の値を増減する
- **大型ボタン**: 再生/停止、TAP、チューナーなど、よく使う操作は大きくして押し外しを防ぐ
- **ラジアルメニュー**: 右クリックで、カーソルの周りに主要な操作を出す
- **キーボード**: スペースキー(再生/停止)、Enterキー(タップテンポ)なども使える
- 専門用語(プラグイン、ドライバなど)は、通常の画面に出さない

---

### 4.4 デザインのコンセプト:「リハーサルスタジオ」【確定】
練習部屋の暖かさと、スタジオでバンドのメンバーと合わせる空気感を再現する。

- **ライトモードは昼のスタジオ、ダークモードは夜のスタジオ**
- **土台は寒色**: 背景と文字は、少し青みのあるグレー。集中しやすく、昼に使ってもまぶしくない
- **アクセントは暖色1色**: アンプの真空管やランプのような琥珀色。寒色の土台に1色だけ暖かい色を置き、落ち着きと個性を両立する
- **バンドの気配**: 音源・ギター・メトロノームを、バンドのメンバーのように見せる。カウントインは、ドラマーのスティックの「1、2、3、4」のように見せる。レベルメーターは、アンプのランプのように光らせる

### 4.5 デザインの原則【確定】
- **練習中は、画面が引っ込む**。演奏中に見るのはタブ譜と、再生・速度・ループだけ
- **1画面に1つの目的**。細かい設定は、すべて設定画面へ
- **専門用語を、通常の画面に出さない**
- **大きな数字を、アプリの「顔」にする**(BPM、速度、時間)

### 4.6 メイン画面(セッション一覧)【提案】
- 置くのは「新しいセッション」ボタン、セッションのカード、設定(歯車)の3つだけ
- カードには、曲名、音源の種類(ファイル/YouTube)、最後に練習した日、前回の速度を表示する
- 最後に練習した順に並べる。**カードをクリックしたら、確認なしで練習画面に入る**(3クリックの1回目)
- 起動時、カードは上から順に短くフェードインする(1枚0.15〜0.2秒、全体で0.3秒程度)。**動きの途中でもクリックできる**ようにし、速さを損なわない。Windowsの設定で「アニメーション効果」がオフなら、動きを省く

### 4.7 色【確定(値は調整可)】
色はデザイントークン(名前付きの値)で管理する。

| トークン | ライト(昼のスタジオ) | ダーク(夜のスタジオ) |
| --- | --- | --- |
| 背景 | `#EEF2F6` | `#1D2025` |
| 面(カードなど) | `#F8FAFC` | `#272B32` |
| 文字 | `#1E2630`(背景との比 13.6:1) | `#E3E7EC`(13.2:1) |
| 補助の文字 | `#5A6573`(5.3:1) | `#9AA3AE`(6.4:1) |
| アクセント(琥珀) | `#B45309`(4.5:1弱。塗りと大きな文字のみ) | `#F0A43A`(7.8:1) |

- 真っ白(`#FFFFFF`)と真っ黒(`#000000`)は使わない
- 文字のコントラスト比は、4.5:1以上を守る
- 既定ではWindowsのテーマに従い、手動でも切り替えられる
- テーマは「トークンの組」として作るので、おまけのテーマ(デスメタルモードなど)も、組を1つ足すだけで追加できる
- チューナーの「合っている/ずれている」は、色だけでなく位置や形でも示す

### 4.8 文字【提案】
- 日本語のUI用フォントと、数字用の個性のあるフォントを組み合わせる
- BPM・速度・時間の数字は、**等幅の数字**にして、値が変わっても表示が揺れないようにする
- フォントはアプリに同梱する(OFLなど、同梱できるライセンスのもの)。具体的な選定は【未決】

### 4.9 描き分けと、ネイティブへの移植【確定】
| 画面 | 描き方 |
| --- | --- |
| セッション一覧、設定 | JUCE(ネイティブ)。起動してすぐ表示できる |
| 練習画面 | WebView(HTML/CSS)。タブ譜とYouTubeを含む |

**進め方**
1. すべての画面を、まずHTML/CSSで試作し、Impeccableでデザインを決める(試作は`design/`フォルダに置き、**見た目の正本**とする)
2. 練習画面は、試作をそのまま本番のコードに育てる
3. 一覧と設定は、決まった見た目をJUCEに移植する。試作と本番の画面を並べて、スクリーンショットで見比べる
4. 見た目を変えるときは、先に試作を直してから移植する

**移植しやすくするための制約(試作の段階から守る)**
- デザイントークンは1つのファイル(`design/tokens.json`)にまとめ、CSSの変数とC++の定数の両方を、そこから作る
- レイアウトは、縦横の並び(flex)と格子(grid)で組む。JUCEにも同じ考え方の部品(FlexBox、Grid)がある
- 影は1つだけ、角の丸みは単純なものにする
- すりガラスのようなぼかし(backdrop-filter)、複雑なグラデーション、CSSのフィルターは使わない
- 動きは、不透明度と位置の変化だけにする(0.15〜0.25秒程度)

### 4.10 自分では変えられない部分【確定】
- YouTubeのプレイヤーと、VST3の編集画面は、相手側の見た目になる。YouTubeは枠で囲み、VST3の編集画面は別のウィンドウで開く
- タブ譜(alphaTab)の色は、テーマに合わせて設定から変える(PoC-3で確認)

## 5. アーキテクチャ

### 5.1 全体構成【提案】

```
┌──────────────────────── アプリ(C++ / JUCE) ─────────────────────────┐
│  [UIスレッド] 画面・操作 ◀──橋渡し(JS⇄C++)──▶ [WebView2(別プロセス)]  │
│        │                                          タブ譜(alphaTab)      │
│        │ コマンド(ロックフリー)                    YouTubeプレイヤー     │
│        ▼                                                │ YouTubeの音   │
│  [オーディオスレッド]                                    ▼               │
│   ギター入力 ─┬─▶ 音色(NAM / VST3) ─┐           Windowsの通常の出力    │
│               └─▶ チューナー解析     │                                  │
│   ローカル音源 ─▶ 速度変更 ──────────┼─▶ ミキサー ─▶ 出力(ASIO/WASAPI) │
│   メトロノーム ──────────────────────┘                                  │
└──────────────────────────────────────────────────────────────────────────┘
```

- 音声処理(C++)と、タブ譜・YouTube(WebView2)を**別プロセスに分ける**。WebViewが重くなっても、音は止まらない
- **起動画面(セッション一覧)はネイティブで描き、表示した直後に裏でWebViewを準備する**。WebViewはアプリの起動中に1つだけ作り、作り直さずに使い回す
- 練習画面のHTMLは、重いフレームワークを使わず軽く作る。ファイルはすべてアプリに同梱し、ネットから読み込まない
- 操作はすべて「コマンド」として扱い、入力元(マウス、キーボード、将来のフットスイッチ)と切り離す

### 5.2 時間の基準(設計の中心)【提案】
タブ譜のカーソル、メトロノーム、ループを、どの「時計」に合わせるかを、音源ごとに切り替える。

| 音源 | 基準の時計 | 精度 |
| --- | --- | --- |
| ローカル音源 | アプリが再生している位置(サンプル数) | サンプル単位で正確。メトロノームもずれない |
| YouTube | YouTubeプレイヤーの再生位置(問い合わせて推定) | 数十msの誤差。ずらし機能で補正する |

### 5.3 スレッドの規約【確定】
- **オーディオスレッド**: メモリ確保・ロック・ファイル操作・ログ出力の待ちを禁止。処理は一定時間内に必ず終える
- **スレッド間の通信**: 数値はアトミック変数、イベントはロックフリーのキューだけで渡す
- **重い処理**(プラグインの検索、ファイル読み込み、BPM取得)は、別のワーカースレッドで行う

## 6. データ設計

セッションファイル(`.gppractice`、JSON)【提案】

```json
{
  "version": 2,
  "title": "曲名",
  "source": { "type": "local", "path": "C:/.../song.mp3" },
  "score": { "path": "C:/.../song.gp", "track_index": 0 },
  "tempo": { "bpm": 120.0, "origin": "score" },
  "playback": { "speed_percent": 100 },
  "sync": { "offset_ms": 0, "points": [] },
  "loop": { "a_ms": 0, "b_ms": 0, "enabled": false },
  "mixer": { "source": 1.0, "guitar": 1.0, "metronome": 0.8 },
  "tone": { "type": "builtin", "preset_id": "clean-01", "vst3": [] }
}
```

- `source.type`は`local`か`youtube`。`tempo.origin`はBPMの出どころ(タブ譜、ネット取得、タップ、手入力)
- `sync.points`は将来の手動同期点用(MVPでは空)

## 8. 技術的な課題とリスク

| 課題 | 内容 | 対応 |
| --- | --- | --- |
| YouTubeの音とASIOの共存 | YouTubeの音はアプリのミキサーを通らず、Windowsの通常の出力から出る | **作者の環境(FocusriteのUSBオーディオインターフェース)では、ASIOでギターを鳴らしながらYouTubeを同時に鳴らせることを確認済み**。他の機材では機材次第のため、動作確認した環境を説明書に明記する |
| YouTubeの埋め込みエラー | パソコン内のファイルとしてページを開くと、YouTubeに「どこに埋め込まれているか」が伝わらず、再生を拒否される(エラー153) | アプリ内でページを`https://`の住所で開く(JUCE・WebView2の機能)。ファイルはローカルのままで、ネットへのアップは不要 |
| 埋め込み禁止の動画 | 一部の動画は埋め込み再生できない | 分かりやすいエラーを表示する |
| YouTubeでのメトロノームの精度 | 再生位置を推定するため、数十msずれる | ずらし機能で補正。精度が足りなければ、YouTubeのときは既定でオフ【未決】 |
| BPM取得の精度 | ライブ版やカバーでは、データの値と実際のテンポが違う | 候補として表示し、手入力・タップで必ず直せるようにする。取得元は差し替えられる設計にする |
| WebView2の起動時間 | 起動や、練習画面を開くのが遅くなる | 起動画面はネイティブで描き、一覧を表示している間に裏でWebViewを準備する(4.9、5.1) |
| 試作とネイティブの見た目のずれ | 一覧画面と練習画面の統一感が崩れる | トークンを共有し、移植しやすい表現だけを使う。スクリーンショットで見比べる(4.9) |
| MVPが大きい | 12月末に間に合わない | 9.3の「削る順番」に従う |

## 9. 計画

### 9.1 技術検証(PoC)

| ID | 内容 | 合格基準 |
| --- | --- | --- |
| PoC-0 | 開発環境(JUCE、CMake、MSVC、Zed)でウィンドウを出す | ビルドして起動できる。Zedでデバッグできるか分かる |

| PoC-4 | YouTubeを`https://`のページに埋め込み、APIで操作し、alphaTabと同期する | 再生・速度変更が追従する。アプリ内でもYouTubeとASIOが共存できる |
| PoC-5 | BPM検索サービスを数曲で比較する | 採用する取得元が決まる |
